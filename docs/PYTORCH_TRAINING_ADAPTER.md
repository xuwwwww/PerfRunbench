# PyTorch Training Adapter

The `pytorch-training` adapter extends PerfRunbench's golden-path workflow to
training workloads while keeping the product centered on reproducible
benchmarking, bounded autotuning, statistical confirmation, and guarded
recommendation apply.

The adapter does not require PyTorch as a core dependency. Production
PerfRunbench code does not import `torch`; the optional synthetic example does
so inside the workload only and skips when `torch` is unavailable.

## Quick Start

```bash
autotuneai init --adapter pytorch-training --output autotune.yaml
autotuneai run --auto --config autotune.yaml -- python train.py
```

`init` refuses to overwrite an existing config unless `--force` is provided.
The generated YAML is a public placeholder config and contains no cloud
targets, credentials, model paths, datasets, or private machine paths.

When tuning inside a Python virtualenv, prefer passing the virtualenv Python
executable explicitly. PerfRunbench preserves executable symlink paths in
launch specs so a virtualenv interpreter is not collapsed to the underlying
system Python interpreter.

## Adapter Contract

Top-level config structures must include `schema_version: "1.0"`.

The training adapter requires:

- `workload.adapter: pytorch-training`
- an explicit objective metric and direction
- a bounded tuning slice
- a progress/result metric source
- allowlisted knob bindings
- a fixed `world_size`
- an effective-batch policy

Unknown adapter fields are rejected. This prevents accidental reliance on
unreviewed parser hooks, private command conventions, or source mutation.

## Allowlisted Knobs

Initial semantic knobs:

- `micro_batch_size`
- `gradient_accumulation`
- `dataloader_workers`
- `dataloader_prefetch`
- `dataloader_pin_memory`
- `dataloader_persistent_workers`
- `cpu_threads`
- `interop_threads`
- `intraop_threads`
- `amp_mode`
- `compile_mode`

AMP and compile modes are opt-in. They are not generated by default and require
an explicit adapter capability declaration before they can be tested.

## Binding Types

Supported bindings are:

- `cli_argument`
- `env_var`
- `boolean_cli_flag`
- `json_config_path`
- `yaml_config_path`
- `adapter_environment`

JSON/YAML config bindings copy the original file into the candidate artifact
directory, mutate only the declared path, retain source and overlay digests,
and update the workload argv to reference the overlay. The original source file
is never rewritten.

Python and TOML mutation are intentionally unsupported.

## Recommendation Scope

Training recommendations are process-scoped. A selected configuration records:

- adapter and protocol versions
- knob values and binding resolution
- baseline and selected effective batch sizes
- semantic-change state
- slice and metric protocol digests
- workload identity and environment fingerprint
- candidate, confirmation, and cache evidence
- canary launch spec and full-run launch spec

The bounded tuning slice is used for candidate search and canary validation.
The full-run launch spec omits the slice control so `run --auto` does not leak
the tuning slice into the user's long training job.

## Claim Boundary

Valid wording:

```text
Best observed eligible configuration under the tested training workload,
slice protocol, and measurement protocol.
```

PerfRunbench does not claim global optimality and does not convert failed,
stalled, or invalid-metric candidates into zero-valued measurements.

## Real Arm Validation

Phase 14B validated the adapter on a real Linux Arm64 / Neoverse-V1 target with
an isolated CPU-only PyTorch environment. The selected synthetic-workload
configuration preserved effective batch size, passed process-scoped canary
validation, reused the RecommendationCache, rejected a hard-drift bundle copy,
and passed downloaded artifact digest validation.
